# 闪惠智购商城 — 技术文档

## 一、项目概述

本项目是面向高并发场景的商品秒杀系统，模拟电商平台限时抢购活动的核心业务流程。系统主要挑战在于：秒杀活动开始瞬间大量用户并发请求同一商品，必须在保证数据一致性（不超卖、不重复下单）的前提下，提供尽可能高的吞吐量与低延迟体验。项目额外集成了 AI 导购模块，支持流式对话与个性化商品推荐。

---

## 三、系统整体架构

```
用户请求
    │
    ▼
[接口安全层]  图形验证码 + 随机动态 Path + @AccessLimit 限流拦截
    │
    ▼
[Redis 缓存层]  preDecrStock() Lua 脚本原子预扣库存（GET 判断 + DECR，库存不足直接返回 -1）
    │  库存充足
    ▼
[RabbitMQ 消息队列]  入队后立即返回"排队中(0)"，客户端轮询结果
    │
    ▼
[MQ Consumer]  二次校验 DB 库存 + 重复订单检查
    │
    ▼
[@Transactional 事务]  DB CAS 扣库存 + 写 order_info + 写 seckill_order
    │
    ▼
[Redis 订单缓存]  写入成功结果，客户端轮询命中后跳转订单详情
```

## 四、核心业务模块

### 4.1 用户模块

**使用工具**：Spring Boot Validation、commons-codec、Redis、ThreadLocal

**方法**：
- 密码安全：登录时执行**双重 MD5**。前端对"明文 + 固定盐"做第一次 MD5，后端对"前端 MD5 结果 + 随机盐"做第二次 MD5 后存库，防止彩虹表攻击与数据库泄露。
- 分布式 Session：登录成功后生成 UUID Token，以 `token → SeckillUser` 存入 Redis 并写入 Cookie。每次请求由 `AccessInterceptor` 从 Cookie / Authorization Header / 请求参数中读取 Token，查询 Redis 恢复用户对象，存入 `UserContext`（ThreadLocal）。
- 参数自动注入：自定义 `UserArgumentResolver`，Controller 方法直接声明 `SeckillUser` 参数即可自动获得当前用户，无需每个方法手动解析 Session。

**解决的问题**：明文密码安全存储；无状态分布式会话，支持水平扩展。

---

### 4.2 商品模块

**使用工具**：MyBatis、Redis、`InitializingBean`

**方法**：
- 商品数据分存于 `goods`（商品基本信息）和 `seckill_goods`（秒杀专属信息：秒杀价、库存、起止时间）两张表，通过 LEFT JOIN 查询组装成 `GoodsVo` 视图对象返回前端。
- `SeckillController` 实现 `InitializingBean` 接口，容器启动完成后执行 `afterPropertiesSet()`，遍历全量商品列表，将每件商品的库存数量以 `GoodsKey:goodsId → stockCount` 的形式**预热写入 Redis**。
- 后续所有库存读写均走 Redis，不查询数据库，大幅降低热点数据对 DB 的压力。

**解决的问题**：将高频读取的库存数据从数据库卸载到缓存，秒杀链路中库存判断的响应时间从毫秒级 DB 查询降至微秒级 Redis 读取。

---

### 4.3 秒杀模块（核心）

**使用工具**：Redis（preDecrStock + rollbackStock）、RabbitMQ、`@Transactional`、`SseEmitter`

#### 请求进入阶段（Controller）

1. **随机 Path 验证**：客户端在点击抢购前须先调用 `/getPath` 接口获取一次性随机 Token 作为 URL 路径段（MD5 加盐生成），只有持有合法 Path 的请求才能到达秒杀接口，防止接口地址被固定爬取。
2. **Redis 原子预扣**：调用 `redisService.preDecrStock()`，内部执行 `DECR` 后检查返回值：
   - 返回值 ≥ 0：预扣成功，继续流程。
   - 返回值 < 0：立即执行 `INCR` 回滚，返回"已售罄"，阻断请求，避免 Redis 库存值持续为负导致后续所有请求被误拦截。
3. **重复订单检查**：查询 `seckill_order` 表（同时查 Redis 缓存），同一用户对同一商品已有订单则直接返回 `REPEAT_SECKILL`。
4. **入队**：通过 `MQSender` 将 `SeckillMessage`（用户 + 商品ID）序列化后发送至 `seckill.queue`，立即向客户端返回 `0`（排队中），不阻塞 HTTP 线程。

#### 异步消费阶段（MQReceiver）

1. 从 MQ 消息中反序列化 `SeckillMessage`，查询商品 `GoodsVo`。
2. **二次 DB 库存校验**：`stockCount <= 0` 则丢弃消息（ACK），防止 Redis 与 DB 短暂不一致时的漏网请求。
3. **二次重复订单检查**：查询 DB 中 `seckill_order`，防止同一消息被重复消费。
4. 调用 `seckillService.seckillWithCache()`，在单个 `@Transactional` 事务中完成：
   - `reduceStock()`：执行 `UPDATE seckill_goods SET stock_count = stock_count - 1 WHERE goods_id = ? AND stock_count > 0`（CAS 写法，影响行数为 0 说明 DB 层已无库存）。
   - `createCacheOrder()`：写入 `order_info` + `seckill_order`，并将订单写入 Redis 缓存（key: `userId_goodsId`）。
5. 若 `reduceStock` 返回 false，调用 `redisService.rollbackStock()` 补回 Redis 库存。

#### 客户端轮询阶段

客户端每隔 500ms 调用 `/seckill/result?goodsId=`，服务端先查 Redis 订单缓存：
- 命中 → 返回订单 ID（秒杀成功）
- 未命中但商品已标记售罄（`SeckillKey:isGoodsOver`）→ 返回 `-1`
- 否则 → 返回 `0`（继续等待）

**解决的问题**：将"秒杀下单"拆解为"预扣 + 入队 + 异步落库 + 轮询"四段，热路径完全绕开数据库写操作，彻底解耦瞬时流量峰值与数据库写压力。

---

### 4.4 订单模块

**使用工具**：MyBatis、`@Transactional`、Redis

**方法**：
- 每次秒杀成功生成两条记录：`order_info`（完整订单，含金额、状态、收货地址）和 `seckill_order`（秒杀专属薄记录，含用户ID、商品ID、订单ID）。
- `seckill_order` 表在 `(user_id, goods_id)` 上设有**唯一索引**，作为数据库层幂等兜底：即使应用层重复订单检查被并发穿透，DB 也会拒绝第二次插入并回滚整个事务。
- `createCacheOrder()` 事务完成后，将 `SeckillOrder` 写入 Redis 缓存（TTL 按 `OrderKey` 配置），用于轮询接口快速命中，避免频繁查询 DB。

**解决的问题**：唯一索引兜底超卖最后一道防线；Redis 缓存订单结果支持高频轮询不打 DB。

---

### 4.5 AI 导购模块

**使用工具**：Claude API（`claude-haiku-4-5`）、`SseEmitter`、`ConcurrentHashMap`、`ExecutorService`

**方法**：
- **流式对话**：`AiGuideController` 接收 POST `/ai/stream` 请求后创建 `SseEmitter`（超时 120s），将流式任务提交至独立的 `CachedThreadPool`，避免阻塞 Spring MVC 线程；后台线程用 `HttpURLConnection` 直连 Claude API（`Accept: text/event-stream`），逐行解析 SSE 数据中的 `content_block_delta` 事件，提取 `text_delta` 字段后通过 `emitter.send()` 实时推送至前端，实现打字机效果。
- **多轮对话记忆**：每个 HTTP Session 对应一条对话历史（`ConcurrentHashMap<sessionId, List<{role,content}>>`），每次对话前将 `user` 消息追加，回复完成后追加 `assistant` 消息，最多保留最近 20 条（超出时 FIFO 淘汰）。
- **个性化推荐**：构建 System Prompt 时，查询数据库获取当前用户最近 5 笔订单记录，注入"用户近期购买历史"上下文，引导模型优先推荐同类或互补商品。
- **实时商品上下文**：每次对话调用 `goodsService.getGoodsVoList()` 获取当前秒杀商品列表（含剩余库存、秒杀价、开抢时间），注入 System Prompt，保证推荐信息实时准确。
- **非流式降级**：提供 `/ai/chat` 同步接口，浏览器不支持 EventSource 时使用，通过 `RestTemplate` 发起普通 POST 请求。
- **多语言支持**：System Prompt 末尾附加语言指令（中文/英文/日文），强制模型以指定语言回复。

**解决的问题**：同步接口等待感差（首字延迟高）→ SSE 流式推送；对话无状态无法追问 → 历史记录保持上下文；推荐缺乏针对性 → 注入用户历史和实时商品数据。

## 五、关键技术方案详解

### 5.1 防超卖：三层递进拦截

超卖是秒杀系统最核心的一致性问题，本项目采用三道递进防线：

**第一道 — Redis `preDecrStock()` Lua 原子预扣（Controller 层，拦截 99%+ 请求）**

```
Lua script (GET + DECR atomic):
  ├─ stock > 0 → DECR，返回新库存值（≥ 0）→ 预扣成功，继续入队
  └─ stock ≤ 0 → 直接返回 -1，不执行 DECR → 返回"已售罄"
```

Lua 脚本在 Redis 端原子执行，GET 判断与 DECR 之间不存在中间态，彻底消除"DECR 后崩溃导致库存永久为负"的风险。

**第二道 — DB CAS 写（MQ Consumer 层，兜底 Redis 与 DB 短暂不一致）**

```sql
UPDATE seckill_goods
SET stock_count = stock_count - 1
WHERE goods_id = #{goodsId} AND stock_count > 0
```

`WHERE stock_count > 0` 是乐观锁写法，影响行数为 0 说明 DB 已无库存，事务回滚，同时触发 Redis 库存回补（`rollbackStock()`）。

**第三道 — `seckill_order` 唯一索引（DB 层，兜底重复下单）**

`(user_id, goods_id)` 联合唯一索引，即使前两道被并发穿透，数据库也会拒绝第二次插入并抛出异常，`@Transactional` 回滚全部操作。注意：此索引防的是**同一用户重复下单**，不防不同用户超卖，超卖防线是前两道。

---

### 5.2 异步削峰：RabbitMQ 解耦热路径

**问题**：秒杀开始瞬间数万请求同时到达，直接写 DB 会将数据库打垮（连接池耗尽、锁争用加剧）。

**方法**：
1. 秒杀接口在 Redis 预扣成功后**只做一件事**：将 `SeckillMessage` 发送至 `seckill.queue` 持久化队列，立即返回 `0`（排队中）。HTTP 请求链路耗时 < 5ms。
2. MQ Consumer 按自身处理能力消费消息，每条消息独立执行 DB 写操作，将流量峰值"拉平"成均匀的消费速率，数据库压力始终在可控范围内。
3. 客户端通过轮询 `/seckill/result` 异步获取结果，先查 Redis 订单缓存，无需每次查 DB。

**效果**：未优化直连 DB 路径 QPS ~703；Redis + MQ 优化后 QPS ~1500，提升约 113%，平均响应时间降至 150ms。

---

### 5.3 接口安全：多维度防刷

单纯的业务逻辑防超卖还不够，需要在请求进入业务层之前就过滤掉恶意流量。

| 机制 | 实现 | 防护目标 |
|---|---|---|
| 图形验证码 | `createSeckillVerifyCode()` 生成含数学运算的干扰图，结果存 Redis，下单前校验 | 阻断机器人自动抢购 |
| 动态接口路径 | `/getPath` 返回 MD5 随机 Token，秒杀 URL 为 `/{token}/seckillWithCacheAndMQ` | 防止接口地址被固定爬取 |
| `@AccessLimit` 注解限流 | 自定义注解 + `AccessInterceptor` 拦截器，Redis 计数器实现滑动窗口（5次/5秒/用户/URI） | 限制单用户高频刷接口 |

`@AccessLimit` 的无侵入设计：在需要限流的 Controller 方法上加注解即可，拦截器自动读取注解参数，Redis key 格式为 `URI_userId`，灵活支持不同接口配置不同阈值。

---

### 5.4 数据一致性保证

**事务边界**：`seckillWithCache()` 和 `createCacheOrder()` 均标注 `@Transactional`，Spring 默认 `REQUIRED` 传播级别，两者共享同一事务，保证"减库存 + 写主订单 + 写秒杀订单"三步原子执行。

**Redis 与 DB 的一致性**：
- 启动时：DB 库存 → Redis（单向同步，以 DB 为准）。
- 秒杀成功后：DB 成功 → Redis 订单缓存写入（后写），两者均成功才算完成。
- DB 扣减失败：`rollbackStock()` 将 Redis 库存补回，避免幽灵扣减导致少卖。

**全局异常处理**：`GlobalExceptionHandler` 捕获未处理异常，统一返回 `Result.error()` 格式，防止异常信息泄露。

---

### 5.5 分布式 Session 设计

Session 不存储在 JVM 内存（Tomcat Session），而是以 `token → SeckillUser(JSON)` 存入 Redis，TTL 随每次访问续期。优点：
- 支持水平扩展，任意节点均可通过 Token 还原用户。
- Token 可通过 Cookie、Header（Authorization）、URL 参数三种方式传递，兼容多端场景。

## 六、性能测试结果

测试工具：JMeter | 测试场景：1000 用户，5000 并发请求同一秒杀商品

| 方案 | QPS | 平均响应时间 | 成功率 |
|---|---|---|---|
| 未优化（直连 DB） | ~703 | 较高 | 存在超卖风险 |
| Redis + MQ 优化 | ~1500 | ~150ms | 99.8% |

优化收益来源：
1. Redis 预扣将绝大多数请求在缓存层拦截，DB 写请求量大幅减少。
2. MQ 将剩余请求异步化，DB 写操作在消费端均匀执行，避免连接池瞬时耗尽。
3. Druid 连接池（最大 50 连接，与 MySQL 默认连接数匹配）在消费端提供稳定的 DB 并发能力。

## 七、已完成的修复

### 7.1 Redis 库存补偿 —— MQReceiver 全面异常兜底

**问题**：原 `MQReceiver` 无 try-catch，事务回滚（如唯一索引冲突）后 Redis 库存永久泄漏，导致假性少卖。

**修复**：
- `receiveSeckill()` 增加方法级 try-catch，任何异常均触发 `redisService.rollbackStock()` 补偿 Redis 库存。
- `reduceStock()` 返回 false 时同样执行回滚。
- 库存不足 / 重复下单属于正常幂等场景，直接 ACK，不消耗重试次数。

---

### 7.2 手动 ACK + 死信队列 —— 彻底消除无限重投

**问题**：自动 ACK + `default-requeue-rejected=true` 导致消费失败的消息无限重投，打满 CPU 和连接池。

**修复**：
- `application.properties` 中设置 `acknowledge-mode=manual`、`default-requeue-rejected=false`。
- `MQConfig` 新增 `seckill.dead.exchange` + `seckill.dead.queue`，主队列绑定死信交换机。
- `MQReceiver` 正常消费调用 `basicAck`，异常时调用 `basicNack(requeue=false)` 将消息路由至死信队列，由人工或定时任务对账补偿。

---

### 7.3 SeckillController 换用 preDecrStock —— 修复库存永久为负

**问题**：原代码调用裸 `decr()`，100 个并发请求在库存只剩 1 时会将 Redis 库存打到 -99，后续所有请求被误拦截，库存"永久售罄"。

**修复**：改用 `redisService.preDecrStock()`，内部通过 Lua 脚本原子执行"GET 判断 + DECR"，保证 Redis 库存值始终 ≥ 0（见 7.7）。

---

### 7.4 有界线程池替换 CachedThreadPool —— 防止 OOM

**问题**：`Executors.newCachedThreadPool()` 最大线程数无上限，并发 AI 请求激增时 JVM OOM，拖垮整个秒杀服务。

**修复**：
```java
new ThreadPoolExecutor(
    Runtime.getRuntime().availableProcessors(), // corePoolSize
    50,                                          // maxPoolSize
    60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(200),              // 有界队列
    new ThreadPoolExecutor.AbortPolicy()         // 满则拒绝
)
```
线程池满时捕获 `RejectedExecutionException`，通过 SSE 向前端推送"服务繁忙，请稍后重试"降级提示。

---

### 7.5 Druid 连接池参数修正

**问题**：`initialSize=100`、`minIdle=500`、`maxActive=1000` 严重超出 MySQL 默认 `max_connections=151`，服务启动时即报 `Too many connections`。

**修复**：调整为 `initialSize=5`、`minIdle=5`、`maxActive=50`，与 MySQL 默认配置匹配，生产环境根据实际 `max_connections` 调整。

---

### 7.6 Path 一次性 Token

**问题**：`checkPath()` 验证通过后未删除 Redis 中的 Path，同一 Token 在 TTL 内可无限复用，绕过 `@AccessLimit` 限流。

**修复**：`checkPath()` 验证通过后立即执行 `redisService.delete(SeckillKey.getSeckillPath, key)`，实现一次性 Token 语义。

---

### 7.7 preDecrStock 升级为 Lua 脚本 —— 消除库存永久冻结中间态

**问题**：`preDecrStock()` 原实现先执行 `DECR`，若结果 < 0 再执行 `INCR` 回滚。两步之间若 JVM 崩溃（OOMKilled、GC overhead），Redis 库存卡在 -1，后续所有请求 `DECR` → -2、`INCR` → -1，进入死循环，商品**永久下架**。

**修复**：用 Lua 脚本将"判断 > 0 则 DECR"合并为 Redis 原子操作，同时消除了原有的 `EXISTS + DECR` 两步 TOCTOU 问题：

```java
String luaScript =
    "local s = tonumber(redis.call('GET', KEYS[1])) " +
    "if s and s > 0 then " +
    "    return redis.call('DECR', KEYS[1]) " +
    "else " +
    "    return -1 " +
    "end";
long stock = (Long) jedis.eval(luaScript, 1, realKey);
return stock >= 0;
```

返回值语义：DECR 后的库存值（≥ 0 表示成功）；-1 表示库存不足（未执行 DECR）。

---

### 7.8 MQ 生产端可靠性 —— Publisher Confirm + 入队异常回滚

**问题**：`MQSender` 原实现使用 `AmqpTemplate.convertAndSend()` 发送后即认为入队成功，但存在两条丢消息路径：
1. **TCP 失败**：网络闪断时，模板重试（`max-attempts=3`）耗尽后抛出 `AmqpException`，而 Controller 没有 catch，Redis 库存永久泄漏（少卖）。
2. **Broker 落盘失败**：Broker 接受了 TCP 连接但在持久化前崩溃，`convertAndSend` 不报错，消息静默丢失，Redis 库存永久泄漏。

**修复**：

*application.properties* —— 开启 Publisher Confirm：
```properties
spring.rabbitmq.publisher-confirm-type=correlated
spring.rabbitmq.publisher-returns=true
```

*MQSender* —— 注册 `ConfirmCallback`，Broker NACK 时异步补偿 Redis：
```java
@PostConstruct
public void init() {
    rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
        if (!ack && correlationData != null) {
            redisService.rollbackStock(GoodsKey.getSeckillGoodsStock,
                                       correlationData.getId());
        }
    });
}
// 发送时携带 goodsId 作为 CorrelationData ID，供回调定位需要回滚的 key
rabbitTemplate.convertAndSend("", MQConfig.SECKILL, (Object) msg, correlationData);
```

*SeckillController* —— catch `AmqpException`（TCP 重试耗尽），同步补偿 Redis：
```java
try {
    mQSender.sendSeckillMessage(mms);
} catch (AmqpException e) {
    redisService.rollbackStock(GoodsKey.getSeckillGoodsStock, "" + goodsId);
    return Result.error(ResultCode.SECKILL_FAIL);
}
```

两条路径组合：TCP 失败 → 同步 catch 回滚；Broker 落盘失败 → 异步 ConfirmCallback 回滚。至此"预扣 Redis → 消息入队"之间的断裂带被完全封堵。

### 7.9 AI 导购对话历史迁移至 Redis —— 支持多实例与自动 TTL 清理

**问题**：`ConcurrentHashMap` 存储多轮对话历史，服务重启即丢失，多实例部署时不同节点会话不共享，导致用户换节点后上下文断裂。

**修复**：
- 新增 `AiHistoryKey`（TTL 24h），key 格式 `AiHistoryKey:h{sessionId}`。
- `RedisService` 新增三个 List 方法：`listAppend()`（RPUSH + LTRIM + EXPIRE 原子 Lua）、`listRange()`（LRANGE）、`listRpop()`（RPOP，用于出错回滚）。
- `AiGuideService` 移除 `ConcurrentHashMap sessions` 字段，替换为：
  - `appendMessage(sessionId, role, content)` — 序列化后写 Redis
  - `getHistory(sessionId)` — 读 Redis 并反序列化
  - `rollbackLastMessage(sessionId)` — RPOP 撤销最后一条
- `clearSession()` 改为 `redisService.delete(AiHistoryKey.history, sessionId)`。

**效果**：任意实例重启后用户对话历史不丢失；多实例负载均衡下任意节点均可还原完整上下文；24h 自动过期无需手动清理。

### 8.1 乐观锁版本号

当前 DB 层 CAS 写法（`WHERE stock_count > 0`）已能防超卖，如需更强的并发控制，可增加 `version` 字段升级为标准乐观锁：

```sql
UPDATE seckill_goods
SET stock_count = stock_count - 1, version = version + 1
WHERE goods_id = #{goodsId} AND stock_count > 0 AND version = #{version}
```
