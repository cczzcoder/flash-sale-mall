# 商品秒杀系统高并发优化计划

> 本计划基于当前工作区代码制定。后续压测只使用优化后的当前版本，**不引用历史压测结果作为新版本容量结论**。

## 总体目标

在保证不超卖、订单幂等和故障可恢复的前提下，逐步提升秒杀系统的吞吐、延迟和可用性。

容量指标必须区分：

- **并发数**：施压机同时运行的线程/用户数。
- **RPS/QPS**：服务端每秒实际完成的请求数。
- **订单吞吐**：每秒完成订单落库的数量。
- **响应时间**：重点观察 P50、P95、P99，而不是只看平均值。

## 核心约束

1. 前端预检不能代替服务端鉴权。收货地址优化应使用服务端签发的短期 `addressTicket`。
2. Redis 预扣库存必须携带唯一 `reservationId`，并有“预扣未落单”超时回补机制。
3. Redis 分桶时必须先做 `userId + goodsId` 幂等锁，避免同一用户落入不同桶产生重复订单。
4. MQ 失败不能无限重投：采用有限次数延迟重试，最终进入死信队列。
5. `prefetch` 不按固定公式设置，必须通过订单处理耗时、unacked 和队列积压实测调节。
6. 当前项目使用 `application.properties` 和 MyBatis，`spring.jpa.show-sql` 对本项目无效。

## 阶段 0：当前版本基线

### 工作内容

- 使用当前代码重新构建和启动环境。
- 清理并准备隔离的商品、用户、订单和地址数据。
- 进行 100、300、500、1000、3000 并发阶梯测试。
- 每档记录 HTTP RPS、P50/P95/P99、非业务错误率。
- 同时记录 MySQL 行锁等待、连接池等待、慢查询，Redis 延迟/连接池等待，RabbitMQ ready/unacked/dead-letter。
- 对账成功订单、DB 库存、Redis 库存和重复订单。

### 验收条件

形成新的基线报告；不使用旧报告推导当前版本容量。

## 阶段 1：秒杀热路径优化

### 工作内容

- 将 Redis 扣库存、MQ 收发、轮询等高频 `INFO` 日志降为 `DEBUG`。
- 生产使用异步日志，并按 1%～5% 采样保留关键请求。
- 增加“本地商品令牌桶 + Redis 全局商品限流”两层限流。
- 增加地址预检接口和短期 `addressTicket`，秒杀提交接口不再直接查询地址表。
- 复用 Redis Lua 脚本 SHA，减少重复脚本传输和无效 GET。
- 为 Redis、MQ、数据库调用设置超时和快速失败。

### 目标

在 300～500 并发下，核心接口 P95 尽量控制在 500ms 内；目标吞吐约 500～800 RPS，最终以阶段 0 复测结果为准。

## 阶段 2：数据库与库存热点优化

### 工作内容

- 保持并验证商品、订单、秒杀订单关键索引。
- 缩短订单事务，仅保留库存扣减和必要的两张订单表写入。
- 将非必要查询移出事务。
- 在数据库连接数、CPU 和锁等待约束下测试连接池 50、80、100。
- 评估库存桶、库存令牌或按商品拆分库存行，降低单商品热点行锁。
- 对“Redis 已预扣但 DB 落单失败”建立可重放、可回补的 reservation 记录。

### 目标

订单落库目标约 200～500 单/秒；库存不超卖，异常时可恢复，不以牺牲一致性换吞吐。

## 阶段 3：RabbitMQ 削峰与重试优化

### 工作内容

- 将消费者并发改为配置项，逐步测试 10、20、30 个消费者。
- 逐步测试 `prefetch=1、5、10、20`，以吞吐提升且 unacked 不持续增长为准。
- 增加延迟重试队列，最多重试 3 次，永久失败进入死信队列。
- 保留 reservation、订单唯一索引和重复消费幂等机制。
- 增加队列积压、消费延迟和死信告警。
- 优化前端排队状态和轮询退避，避免轮询流量反向冲击系统。

### 目标

秒杀提交与订单落库解耦；突发流量下队列可恢复，目标排队结果大部分在 5 秒内完成，最终以实测为准。

## 阶段 4：Redis 高并发与热 Key 优化

### 工作内容

- 升级 Redis 客户端并评估 Sentinel/Cluster。
- 对单商品库存进行分桶，Lua 内完成用户幂等标记和库存桶选择。
- 设计 Redis 重启后的库存重建流程：AOF/持久化、reservation 扫描、DB 订单对账。
- 监控热 Key、命令延迟、blocked clients、内存淘汰和连接池等待。

### 目标

Redis 不成为单商品突发流量的首要瓶颈；重启和故障恢复后库存不超卖、不长期少卖。

## 阶段 5：应用集群与业务隔离

### 工作内容

- 部署 2～4 个无状态应用实例并增加负载均衡。
- 将秒杀、普通查询、订单查询、管理后台和 AI 导购隔离线程池和限流策略。
- 确保 Session、限流和幂等状态在 Redis 中统一共享。
- 限制 Actuator/Prometheus 管理端点访问范围。

### 目标

单个应用实例故障不影响整体秒杀；普通业务和 AI 导购不会拖垮秒杀链路。

## 阶段 6：高可用与故障降级

### 工作内容

- MySQL 主从/高可用、Redis Sentinel/Cluster、RabbitMQ 集群。
- 增加熔断、舱壁隔离、超时、降级和自动摘除故障实例。
- 演练 Redis、MySQL、RabbitMQ 重启和短暂网络中断。
- 验证消息重复、ACK 失败、数据库写入失败和库存回补。
- 建立死信人工处理和库存/订单定期对账机制。

### 目标

核心下单链路具备故障降级能力，组件局部故障不扩散为全站故障。

## 阶段 7：最终容量验收

每完成一个阶段都必须使用当前版本重新压测。最终报告至少包含：

| 场景 | 验收方向 |
|---|---|
| 300 并发 | P95、错误率、队列无持续积压 |
| 500 并发 | 非业务错误率目标 < 0.1% |
| 1000 并发 | 可排队、可恢复、无超卖 |
| 3000 并发 | 有限流和降级，不崩溃 |
| 5000 并发 | 仅在集群环境验证，不从单机推断 |
| 所有场景 | 超卖率 0%、重复订单 0、库存最终一致 |

## 执行顺序

展示版优先执行：**阶段 0 → 阶段 1 → 阶段 2 → 阶段 3**。

生产级建设再执行：**阶段 4 → 阶段 5 → 阶段 6 → 阶段 7**。

每次只推进一个阶段，完成代码、测试、压测和报告后再进入下一阶段。
